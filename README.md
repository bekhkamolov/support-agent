# Support Agent

A customer-support AI agent for a fictional online shop ("Nordwind"): it answers questions from
policy documents with retrieval-augmented generation (RAG), checks orders and starts returns through
tool calls, and hands off to a human when it is not confident. The focus of the project is a
**reproducible evaluation harness**: every design choice is backed by a measured number.

> Status: **Day 3 – tool-calling agent.** Systematic agent evaluation (Day 4), tracing, API and
> deployment follow.

## Retrieval evaluation

52 questions, each labelled with the policy document(s) that answer it. Questions are tagged
`lexical` (they share key words with the answer document) or `paraphrase` (same meaning, different
words). Metrics are computed at document level: recall@k and mean reciprocal rank (MRR).

```bash
python scripts/eval_retrieval.py --retrievers bm25
python scripts/eval_retrieval.py --retrievers bm25,dense,hybrid --embedder mistral
```

### Results

| retriever | recall@1 | recall@3 | recall@5 | MRR | recall@5 lexical | recall@5 paraphrase |
|---|---|---|---|---|---|---|
| BM25 | 0.615 | 0.731 | 0.769 | 0.696 | 1.000 | 0.657 |
| Dense (mistral-embed) | 0.885 | 1.000 | 1.000 | 0.942 | 1.000 | 1.000 |
| Hybrid (RRF, BM25 + dense) | 0.712 | 0.885 | 0.942 | 0.801 | 1.000 | 0.914 |

Median query latency: BM25 0.1 ms, dense 173 ms, hybrid 190 ms (dominated by the embedding API
call for the query).

**Observation:** BM25 retrieves every lexical question but misses about a third of the paraphrased
ones (e.g. "Can I turn my voucher balance into cash?" vs. a document that talks about *gift cards*).
Dense retrieval closes that gap completely. Hybrid retrieval is *worse* than dense alone: RRF weights
both rankings equally, so BM25's wrong documents on paraphrased questions push correct ones down.
On this corpus, unweighted hybrid is not worth its extra complexity; a weighted fusion or a reranker
is evaluated later.

**Limitations:**
- The corpus is small: 24 documents give only 25 chunks, so recall@5 means finding the right
  document among the top ~20% of the corpus. recall@1 and MRR are the more informative columns.
- The questions were written by the same person as the documents, which can make lexical
  questions easier than real customer messages. The labelled set will be extended with messages
  from a public customer-support dataset.

## RAG answers (Day 2)

The pipeline retrieves the top 5 chunks with dense retrieval, sends them with the question to the
chat model and gets back a **Pydantic-validated structured answer**:

```python
class RagAnswer(BaseModel):
    answer: str
    cited_doc_ids: list[str]
    confidence: Literal["high", "medium", "low"]
```

```bash
python scripts/ask.py "Can I send back earrings I bought last week?"
python scripts/eval_rag.py              # 52 questions, prompt caching off vs. on
```

Model: `ministral-14b-latest` (open-weight, Apache 2.0), temperature 0. Answer *correctness* needs
reference answers and an LLM judge (Day 4); what is measured here can be checked automatically.

### Results

52 questions, k = 5. Cached share = cached prompt tokens / prompt tokens.

| run | gold doc retrieved | gold doc cited | only gold docs cited | invented citations | schema errors | prompt tokens | cached share | generation ms (median / p95) |
|---|---|---|---|---|---|---|---|---|
| cache key off | 1.000 | 0.981 | 0.846 | 0 | 0 | 755 | 14% (106) | 1470 / 2651 |
| cache key on | 1.000 | 0.981 | 0.846 | 0 | 0 | 755 | 35% (261) | 1739 / 3309 |

**Observations:**
- **Structured output is reliable:** 0 of 104 responses failed schema validation, and the model never
  cited a document that was not retrieved. Invented citations would be removed in code anyway.
- **Citations are mostly right but noisy:** the gold document is cited in 51/52 answers, but in
  7 answers the model also cites a neighbouring document (e.g. `exchanges` + `sizing`).
- **One systematic miss (q39, "Can I turn my voucher balance into cash?"):** the `gift-cards`
  document was retrieved, but the model did not link *voucher* to *gift card*. Without the cache key
  it cited `price-match` (wrong source); with it, it gave the right fact with no citation and low
  confidence. Temperature 0 did not make the two runs identical.
- **Self-reported confidence is not useful as a signal:** 51/52 answers are "high". The Day 3
  escalation guardrail therefore cannot rely on it and will use retrieval scores instead.
- **Prompt caching:** Mistral caches prompt prefixes automatically. Even without a cache key, 25/52
  requests had the 221-token system prompt cached; with `prompt_cache_key`, 51/52 did (some also
  reused retrieved excerpts, up to 477 tokens). Cached share rose from 14% to 35% of prompt tokens.
  **Latency did not improve** (median 1470 → 1739 ms): with ~755-token prompts, prompt processing is
  a small part of generation time, and the two runs ran sequentially, so the difference is mostly
  API load. Caching is expected to matter for long static prefixes (few-shot examples, tool
  definitions in the agent) and will be re-measured there.
- One wrong answer was found by hand: for earrings the model added a condition ("as long as they are
  unopened") that applies to a different item in the same policy. Answer correctness is measured
  on Day 4.

## Agent (Day 3)

A [PydanticAI](https://ai.pydantic.dev) agent (`ministral-14b-latest`) with four tools:

| tool | what it does |
|---|---|
| `search_policies(query)` | dense retrieval over the policy documents (the Day 2 RAG step as a tool) |
| `get_order_status(order_id, email)` | order lookup in a SQLite mock database (8 demo orders) |
| `start_return(order_id, email, skus, reason)` | starts a return; all return rules are checked in code |
| `escalate_to_human(reason, summary, order_id?)` | creates a support ticket |

```bash
python scripts/chat.py                      # interactive
python scripts/chat.py -m "I want to return my jeans" -m "NW-100001, anna@example.com"
```

**Where the rules live.** The model decides *which* tool to call; it never decides whether a
return is allowed. `orders.py` enforces the return window (30 days from delivery, 60 for
Nordwind Plus), non-returnable categories (earrings, opened cosmetics, ...) and the EUR 6.95 label
fee outside Germany/Austria. Tool inputs are Pydantic-validated (e.g. order number `^NW-\d{6}$`);
invalid input is sent back to the model before the tool runs.

**Safety checks in code**, each added after a failure seen in live testing:

| check | live failure that motivated it |
|---|---|
| Order number and e-mail must appear in what the customer wrote | Model invented `NW-123456` / `customer@example.com` and looked them up repeatedly |
| Identical tool calls are not executed twice; max. 8 model calls per message, then hand-over | The same call repeated until PydanticAI's limit of 50 requests |
| Output validator: no links, and a charged return fee must be stated correctly | Tool charged EUR 6.95, model told the customer "no label fee applies"; model invented a URL |
| Wrong e-mail and unknown order give the same answer | (by design) order numbers cannot be probed |

### Escalation guardrail: calibration

The plan was to escalate when retrieval confidence is low. `scripts/calibrate_guardrail.py`
compares the top-1 dense retrieval score of the 52 answerable questions with 16 questions no
policy covers (10 *near* the shop's topics, e.g. "Is there a student discount?", 6 *far*, e.g. "What
is the capital of Australia?").

| | n | min | median | max |
|---|---|---|---|---|
| answerable | 52 | 0.605 | 0.758 | 0.840 |
| out of scope, near | 10 | 0.669 | 0.715 | 0.749 |
| out of scope, far | 6 | 0.630 | 0.659 | 0.791 |

**The scores overlap too much for a score threshold to be the guardrail.** The threshold with the
best balanced accuracy (0.723) would escalate 11 of 52 answerable questions (21%) and still let
2 of 16 out-of-scope questions through.

| threshold | answerable escalated | near caught | far caught |
|---|---|---|---|
| 0.62 | 1/52 | 0/10 | 0/6 |
| **0.66 (used)** | **1/52** | **0/10** | **4/6** |
| 0.68 | 3/52 | 4/10 | 4/6 |
| 0.70 | 5/52 | 5/10 | 5/6 |
| 0.723 (best balanced) | 11/52 | 9/10 | 5/6 |

So the guardrail has two layers:
1. **Score floor at 0.66 (code):** below it, no excerpts are shown to the model and the
   conversation is handed over even if the model tries to answer. It costs 1 unnecessary
   hand-over in 52 ("My laptop broke after 8 months", a warranty case) and catches most clearly
   off-topic questions.
2. **Model judgement:** for near-topic questions, the model is instructed to escalate when the
   excerpts do not clearly answer the question. How often it does is measured on Day 4.

The floor is checked against the better of the customer's message and the model's search query,
because the threshold was calibrated on customer questions: in live testing the model searched
"return jacket changed mind" (0.625) for an answerable question and was wrongly escalated.

**Status of the live testing:** about 15 manual test conversations, not a benchmark. Still open from
those: the model sometimes adds unsupported details (it called the order date the shipping date,
and once promised delivery "in 2–4 business days"). Rules cannot catch these; the Day 4 LLM judge
for groundedness will.

## Design decisions

| decision | why |
|---|---|
| Chunks of 80 words, 20-word overlap, title prepended | Policy documents are short; 80 words keeps one rule per chunk, overlap avoids cutting a rule in half, the title keeps the topic in short chunks. |
| Dense retrieval (`mistral-embed`) as default | Best recall@1 / MRR on the labelled set; unweighted hybrid (RRF) was worse because BM25 adds wrong documents on paraphrased questions. |
| Embeddings cached on disk by content hash | Re-running the evaluation does not re-embed the corpus (cost, rate limits, reproducibility). |
| Retry with exponential backoff on HTTP 429, fail fast when the plan's limit is 0 | Free-tier rate limits; retrying cannot help when a model is not included in the plan. |
| `ministral-14b-latest` as chat model | Strongest chat model available on the project's API plan; open-weight, so it can also be self-hosted. |
| Structured output via strict JSON schema + Pydantic | The answer is consumed by code (citations, escalation), so it must parse every time. Schema violations are counted, not hidden. |
| Confidence as `high / medium / low`, not a number | LLMs report poorly calibrated numeric scores; labels with written definitions are easier to check. (Measured: still not informative, see above.) |
| Citations checked against the retrieved documents in code | The model cannot cite a source it was not given; any such citation is removed and counted. |
| Static system prompt first, question and excerpts after | Lets the provider cache the prompt prefix; the effect is measured, not assumed. |
| Excerpts wrapped in `<excerpt>` tags and marked as data | Basic protection against instructions hidden in retrieved text (prompt injection). |
| Unit tests use fake embedder and fake LLM | Tests and CI run without network or API keys. |
| PydanticAI for the agent | Typed tools and outputs with Pydantic validation, provider-agnostic, and a scripted `FunctionModel` for testing exact tool-call sequences offline. |
| Business rules in tools, not in the prompt | A return decision must be correct every time; code is testable, a prompt is not. |
| Order lookups need order number + e-mail | Order data is personal; a guessed order number alone must not reveal anything. |
| Retries per model request (SDK retry config), not per agent run | Re-running a whole agent run could repeat a side effect such as `start_return`; returns are also idempotent. |
| Request limit (8 per message) with hand-over on failure | Bounds cost when the model loops; the customer gets a ticket instead of an error. |
| Escalation guardrail = calibrated score floor + model judgement | Retrieval scores of answerable and unanswerable questions overlap (see calibration); a single threshold either escalates too much or catches too little. |
| Demo data fixed to a reference date (2026-10-10) | Return-window results are reproducible in tests and evaluation. |
